CloudFormation Parameters Reference

CloudFormation Parameters Reference

Section titled “CloudFormation Parameters Reference”

This page lists every parameter of the main LMA template, lma-main.yaml, in the groups and order the CloudFormation console shows them. You set these when you create the stack, and change them with a stack update; see Stack Updates & Upgrades.

Some of LMA’s behaviour is not set here at all but on the web UI’s Configuration page, where an Admin changes it while the stack runs. That page, and which settings it holds, are described in the Configuration Guide.

How to read this page

Section titled “How to read this page”

Each parameter has a kind, which says what changing it does:

  • Resource parameters decide which resources the stack creates or how they are built — whether a nested stack exists, an IAM permission, networking, capacity, a retention rule, an alarm. A stack update that changes one changes resources.
  • Configuration page default parameters set the default of a setting an Admin can change on the Configuration page while the stack runs. The entry names the setting. The stack writes the parameter’s value into the configuration as that setting’s default, so a stack update that changes the parameter applies wherever nobody has changed the setting on the page, and a value saved on the page takes precedence until it is reset to the default there. The parameter is kept so that existing deploy commands, pipelines and new installs work as before. A parameter that also reaches a resource, such as a bucket lifecycle rule, stays a Resource parameter, and its entry names the setting it is also the default of.
  • Configuration page limit parameters are the default of a setting and also its upper limit: an Admin can set a lower value on the Configuration page and not a higher one, and every reader uses the smaller of the two. Only the retention settings work this way; see Retention: settings the stack limits.
  • Read at run time parameters reach the application only as a value it reads: an environment variable of a function or task, or a deployment setting. A stack update that changes one changes only the configuration of whatever reads it; for a value built into the web app, that means the web app is rebuilt. The entry says what reads it and when, because that is when a change takes effect: a function reads its environment on each cold start, and a Virtual Participant reads its own when it starts. Where the entry says a value is checked while the stack deploys, a value that fails the check fails the update.
  • Credential parameters are secrets, the ARNs of secrets, or the identifier paired with one. They are held in AWS Secrets Manager.
  • A Deployment check is read only while the stack is being deployed.
  • No effect marks a parameter the template still declares and nothing reads, kept so that deploy commands and pipelines that pass it go on working.

The reference below is generated from the template by scripts/cloudformation_parameters_doc.py, and a test fails when the two disagree. The description under each parameter is the one the console shows.

AdminEmail

Section titled “AdminEmail”

Console label: Admin Email Address

  • Default: (required)
  • Allowed values: Matches ^[\w.+-]+@([\w-]+\.)+[\w-]{2,6}$
  • Kind: Resource. Creates the administrator’s Cognito user and subscribes the address to the operational alerts topic.

Email address of the admin user (e.g. jdoe+admin@example.com) that has access to all meetings for administrative purposes. An initial temporary password will be automatically sent to this user via email.

AllowedSignUpEmailDomain

Section titled “AllowedSignUpEmailDomain”

Console label: Authorized Account Email Domain(s)

  • Default: (empty)
  • Allowed values: Matches ^(|([\w-]+\.)+[\w-]{2,6}(, *([\w-]+\.)+[\w-]{2,6})*)$
  • Kind: Resource. Decides whether the Cognito sign-up check exists, and is read by it and by user management.

Email address domain (example.com) or comma separated list of email domains (example1.com, example2.com) allowed to signin and signup using the web UI. If left empty, signup via the web UI is disabled and users will have to be created using Cognito.

VPLaunchType

Section titled “VPLaunchType”

Console label: VP Launch Type (LAMBDA MICROVM, FARGATE or EC2)

  • Default: MICROVM
  • Allowed values: FARGATE, EC2, MICROVM
  • Kind: Resource. Decides whether Virtual Participants run on EC2 hosts, Fargate tasks or Lambda MicroVMs, and which of those resources exist.

Compute platform for Virtual Participant containers. MICROVM (default): AWS Lambda MicroVMs — each meeting runs in its own Firecracker microVM resumed from a snapshot. Live view ready in ~20-25s, billed per meeting rather than per warm instance, and needs no load balancer, no autoscaling and no OS patching. Requires a region where Lambda MicroVMs are available (us-east-1, us-east-2, us-west-2, ap-northeast-1, eu-west-1 — not GovCloud); meetings are capped at 8 hours. EC2: Warm instances with cached images; ~$33/month per always-on instance, plus autoscaling and OS patching to manage. Use where MicroVMs are unavailable and startup latency matters. FARGATE: Serverless, ~$2/month base, but 1-2 minute startup. Use where MicroVMs are unavailable and cost matters more than latency.

VPInstanceType

Section titled “VPInstanceType”

Console label: VP EC2 Instance Type

  • Default: t3.medium
  • Allowed values: t3.medium, t3.large, t3.xlarge, c5.large, c5.xlarge, c5.2xlarge, m5.large, m5.xlarge
  • Kind: Resource. Sets the instance type of the Virtual Participant EC2 launch template.

EC2 instance type for Virtual Participant (only used if VPLaunchType=EC2). t3.medium recommended for basic transcription. For voice assistant + Simli avatar workloads, use c5.xlarge or larger for sustained CPU performance (no burstable throttling).

VPMinInstances

Section titled “VPMinInstances”

Console label: VP Minimum Warm Instances

  • Default: 1
  • Allowed values: 0 to 10
  • Kind: Resource. Sets the minimum and desired size of the Virtual Participant Auto Scaling group.

Minimum number of warm EC2 instances (only used if VPLaunchType=EC2). Set to 1 for fastest startup, 0 to save costs when not in use.

VPMaxInstances

Section titled “VPMaxInstances”

Console label: VP Maximum Instances

  • Default: 10
  • Allowed values: 1 to 100
  • Kind: Resource. Sets the maximum size of the Virtual Participant Auto Scaling group.

Maximum number of EC2 instances for scaling (only used if VPLaunchType=EC2).

MeetingAssistService

Section titled “MeetingAssistService”

Console label: Meeting Assist Service

  • Default: STRANDS_BEDROCK

Section titled “TavilyApiKey”

Console label: Tavily API Key for Web Search (STRANDS_BEDROCK only)

  • Default: (empty)
  • Allowed values: Must be empty or a valid Tavily API key (20+ characters)
  • Kind: Credential. Stored in a Secrets Manager secret the meeting assistant reads.

(Optional - STRANDS_BEDROCK only) API key for Tavily web search service to enable web search tool. Get your API key from https://tavily.com. When provided, the Strands agent can search the web for current information during meetings. Leave blank to disable web search capability.

TavilyApiKeySecretArn

Section titled “TavilyApiKeySecretArn”

Console label: Existing Secret ARN Holding the Tavily API Key (Optional)

  • Default: (empty)
  • Allowed values: Must be empty, or the ARN of a Secrets Manager secret (arn:aws:secretsmanager:<region>:<account>:secret:<name>).
  • Kind: Credential. Grants the meeting assistant read access to the named secret.

(Optional) ARN of an existing Secrets Manager secret whose value is the Tavily API key. Use this instead of TavilyApiKey when the key is already provisioned in Secrets Manager. Supply one form or the other, not both. A secret encrypted with your own KMS key must grant kms:Decrypt to the meeting-assist function’s role in that key’s policy.

Scaling the WebSocket transcriber

Section titled “Scaling the WebSocket transcriber”

The five Transcriber* parameters size the Fargate service that terminates the browser and desktop-app WebSocket connections (the Stream Audio tab, the Desktop Capture App and the browser extension). They do not affect the Virtual Participant.

Running more than one task requires EnableVideoRecording to be false, and the stack rejects the combination at deploy time rather than failing per meeting. With video recording enabled, the desktop capture app sends meeting video over a second WebSocket connection, and only the task already hosting that meeting’s audio session can attach it. The load balancer in front of the service does not pin a client to a task, and cookie-based stickiness is not available because the CloudFront distribution in front of it forwards no cookies, so with several tasks the video connection is refused whenever it lands on a different task from the audio. EnableVideoRecording also governs Virtual Participant video, which has no such constraint, so scaling the transcriber means giving up desktop app video recording specifically. Audio is unaffected either way: a meeting’s audio uses one connection for its whole lifetime.

Auto scaling adds capacity but never removes it. Taking a task away would end the meetings it is hosting once the load balancer’s deregistration delay elapses, and a meeting can run for hours. So capacity ratchets up and stays there: while TranscriberAutoScalingEnabled is true, Application Auto Scaling owns the task count and a stack update does not reset it to TranscriberDesiredTaskCount. To bring it back down, either set TranscriberAutoScalingEnabled to false — which hands the count back to CloudFormation and applies TranscriberDesiredTaskCount — or reduce it directly with aws ecs update-service --desired-count or aws application-autoscaling register-scalable-target. Budget for the high water mark, not the average. The CPU target is kept below the load at which a task reports itself unhealthy to the load balancer, so that scaling out happens before tasks start being replaced.

A rolling deployment briefly runs up to twice the task count, which is the one window where more than one task exists even with video recording enabled. That is harmless in practice: the draining task keeps serving the sessions already attached to it and the new task only receives new meetings, so no meeting is ever split across the two.

The on-demand speech engine

Section titled “The on-demand speech engine”

EXPERIMENTAL — not production ready. Transcript quality is below Amazon Transcribe’s and defaults may change between releases. Amazon Transcribe remains the recommended engine for production meetings.

EnableMicrovmAsr is the only deploy-time question for this engine. A meeting it transcribes does not go through Amazon Transcribe, so the redaction, custom vocabulary, custom language model and language identification parameters do not apply to it. Two more values are fixed in the AsrDefaults mapping in lma-main.yaml rather than asked: ModelBundle, which models the MicroVM image is built from (parakeet-tdt-v3-live-nemotron35-sortformer by default), and MaxMeetingSeconds (14400), the hard lifetime ceiling per MicroVM. Which meetings use the engine is chosen in the Transcription Engine section of the Configuration page, with no stack update. The bundles, their licences and how one is selected are described in On-demand ASR & Speaker Diarization.

Voice enrollment (Beta)

Section titled “Voice enrollment (Beta)”

[!IMPORTANT] Off by default, and turning it on means storing biometric data about people. Read Voice Enrollment before enabling it.

While EnableVoiceEnrollment is false the tables, the consent portal and the matching step do not exist in the deployment at all. Both enrolling and matching need EnableMicrovmAsr=true, because that engine is what computes speaker embeddings; with enrollment on and that engine off, the tables, the portal and the consent log all exist and work, and the step that would create a voiceprint reports that the engine is missing.

VoiceEnrollmentRetentionDays and VoiceEnrollmentTermsVersion are read only by application code, but they are stack parameters on purpose and are not on the Configuration page. The retention period is stated in the consent terms, and each enrollment records the terms it agreed to, so changing either value asks everybody to consent again. That should be a deliberate deployment, not a save in the web UI.

Virtual Participant capacity and meeting-end detection

Section titled “Virtual Participant capacity and meeting-end detection”

VPInstanceType, VPMinInstances and VPMaxInstances apply only to VPLaunchType=EC2. Under MICROVM, the default, there are no hosts to size or scale: each meeting gets its own MicroVM, billed for its lifetime. See MicroVM launch type.

Reaching Amazon Nova Sonic in another region

Section titled “Reaching Amazon Nova Sonic in another region”

Setting AmazonNovaSonicRegion also grants the Virtual Participant permission to invoke the Nova model in that region. Only the Nova Sonic model moves: the Virtual Participant’s other Bedrock calls, the configuration it reads and the meeting-assistant function the voice assistant calls as a tool all stay in the stack’s region. Nothing checks that Nova Sonic is available in the region you name — check the Amazon Bedrock model support by region table first. A region where the model is not enabled fails at the first voice interaction, with a Bedrock validation error in the Virtual Participant’s logs, not at deploy time.

Monitoring

Section titled “Monitoring”

EnableOperationalAlarms creates the CloudWatch alarms that notify the operational alerts SNS topic; the topic and the dashboard are created either way, so false removes the notifications rather than the visibility. The default TranscribeConcurrentStreamAlarmThreshold is 80% of the default account quota of 25 concurrent streams; raise it if you raise the quota, because the alarm cannot read it. See Monitoring & Alerting.
