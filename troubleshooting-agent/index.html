AI Troubleshooting Agent

AI Troubleshooting Agent

Section titled “AI Troubleshooting Agent”

An agent that answers “why did this fail?” about a deployed LMA stack by reading that stack’s own CloudWatch logs, its Virtual Participant records and its CloudFormation parameters, and reporting a cause together with the evidence it rests on. It is built on the Strands Agents SDK and Amazon Bedrock, the same stack the Meeting Assistant uses.

It reads and does not change anything it diagnoses: no permission to restart, delete or redeploy, and no ability to write to any table or bucket. The grants that are not reads do not touch the deployment either: publishing a progress step to the UI through a single GraphQL mutation, cancelling a log query it started, writing its own log stream, and sending its own X-Ray traces.

Why it exists

Section titled “Why it exists”

Diagnosing LMA means reading several CloudWatch log groups in the right order. A meeting that produced no transcript looks identical whether the WebSocket upgrade was refused, the speech engine declined the stream, the Kinesis consumer threw, or the Virtual Participant never got into the meeting — and the evidence that distinguishes those lives in four different log groups whose names cannot be derived from the stack name you typed.

The agent does that reading. It does not replace Troubleshooting or Monitoring & Alerting; it is the thing to reach for once an alarm or a user report has told you something is wrong and you need to know what.

Using it

Section titled “Using it”

There are three ways to ask the agent a question: the Troubleshooting page, the Diagnose button on a meeting or a Virtual Participant, and the AWS CLI or SDK.

The Troubleshooting page

Section titled “The Troubleshooting page”

Every web UI entry point to the agent is for members of the Admin group.

Members of the Admin group see Troubleshooting in the web UI’s navigation. The page asks questions about the whole deployment, such as “Why didn’t my last Virtual Participant join its meeting?” or “Are there errors in the transcriber in the last hour?”. Type a question, or choose one of the suggested questions shown on an empty page, and choose Ask. The optional Scope section takes a Meeting ID or a Virtual Participant ID to point the agent at one resource.

The answer is shown in the agent’s three sections, described in What it answers with, with the Evidence section collapsed. A diagnosis usually takes one to four minutes, and the page shows how long the current one has been running. One question runs at a time: each run is paid for, so the next question waits until the last one is answered. Earlier questions and their answers stay on the page until you leave it; they are not kept anywhere you can return to.

A user outside the Admin group who opens the page is told that it is for administrators.

The Diagnose button

Section titled “The Diagnose button”

The meeting page’s header and the Virtual Participant detail page’s header each have a Diagnose button, shown to members of the Admin group only. It opens a window and starts a diagnosis of that meeting or Virtual Participant.

There is nothing to type. The diagnosis asks a fixed question for the resource: for a Virtual Participant, whether it joined the meeting and, if it failed or ended early, why; for a meeting, whether it was captured and transcribed from start to end and, if anything failed, why. Closing the window does not stop the diagnosis, and opening it again shows the same one, running or finished. Run again starts a new one.

How the web UI runs a diagnosis

Section titled “How the web UI runs a diagnosis”

A diagnosis takes longer than an AppSync request is allowed to, so the web UI runs it as a job through two GraphQL fields:

FieldWhat it does
startTroubleshooting(input: {Question, CallId, VirtualParticipantId})Checks who is asking, records a job with status PENDING, starts it, and returns it at once.
getTroubleshootingJob(JobId)Returns the job — PENDING, RUNNING, COMPLETED with its Answer, or FAILED with its Error — to the Admin who started it, and to no one else. The page reads it every three seconds.

Both fields are declared for the Admin group in the GraphQL schema, and the AI stack’s troubleshooting resolver function (lma-ai-stack/source/lambda_functions/troubleshooting_resolver) checks the group again before it records anything. A request naming a CallId or a VirtualParticipantId that does not exist is refused.

Question is asked as written. When it is empty, a job scoped to a meeting or Virtual Participant asks the fixed question for that resource, as the Diagnose button does, and an unscoped job asks for the most recent failure in the deployment.

The job then runs in an asynchronous invocation of the same resolver function, which invokes the agent synchronously, once, and writes the answer to the job. Neither invocation is retried, because a retry is a second diagnosis paid for from the start. Jobs are kept in the AI stack’s TroubleshootingJobsTable DynamoDB table for seven days, then removed by its time-to-live setting. A job that is still PENDING or RUNNING seven minutes after it last changed is reported as FAILED with “The diagnosis did not finish”, since the function that ran it has stopped by then.

The answer the web UI shows is the agent’s answer. When the agent reports an error, the job carries the agent’s fixed error message rather than the underlying exception text; that text is in the agent function’s log.

From the AWS CLI or SDK

Section titled “From the AWS CLI or SDK”

The function’s ARN is a stack output, TroubleshootingAgentFunctionArn:

The function returns {"statusCode": ..., "body": "<json>"}, so the diagnosis is inside the encoded body. Writing to a file rather than /dev/stdout keeps the CLI’s own response metadata out of the way. Read the whole body — the token usage and the truncated flag as well as the answer — with jq -r '.body | fromjson' diagnosis.json.

Accepted fields, all optional except that a query is strongly advised:

FieldMeaning
queryThe question. Defaults to “diagnose the most recent failure”.
vpIdA Virtual Participant id to scope the investigation to.
callIdA meeting id to scope to. Also the channel thinking steps stream on.
messageIdWhen present together with callId, each tool call is streamed to the UI’s thinking-step panel over the existing onAddChatToken subscription. The web UI’s jobs do not send one.

Invoking the function directly needs an IAM principal that holds lambda:InvokeFunction on it. The stack grants that only to the AI stack’s troubleshooting resolver role, so unless you already have it through a broad account-level policy such as an administrator role, you have to grant it deliberately. A direct invocation is authorized by IAM alone; the access rule above belongs to the web UI’s two GraphQL fields.

What it answers with

Section titled “What it answers with”

Three sections, always in this order:

The answer starts at ## Root Cause: anything the model writes before that heading is removed before the answer is returned (or before its first ## heading, if the model left out ## Root Cause). Each log line search_logs returns carries the log group and stream it came from, and the Evidence section quotes those values rather than a group name the model recalls, so a line is cited against the group that actually holds it.

Not determined, with the missing evidence named, is a deliberate and acceptable answer. The prompt forbids offering likely causes: a diagnosis you cannot check is worse than none, because you act on it.

What it reads

Section titled “What it reads”

Four tools, each read-only:

ToolReadsWhy
get_stack_parameterscloudformation:DescribeStacks on your LMA stackWhich components this deployment actually runs, and therefore where evidence can exist at all.
discover_log_groupslogs:DescribeLogGroups, plus cloudformation:ListStackResources to resolve this deployment’s own nested stacksThe log group names, their owning component, and how many bytes each holds.
search_logsCloudWatch Logs Insights (logs:StartQuery)Every “why”, timeline, count and cross-component correlation.
get_vp_recorddynamodb:GetItem on the VirtualParticipant tableOne Virtual Participant’s current status, its structured exit code, and — when it was ended from outside — when and why (endedAt, endReason).

get_stack_parameters returns parameter values, because deployment configuration is what the agent is reading them for — but any parameter whose name suggests a credential, an email address or other personal data is reported by name only. That is defence in depth rather than the control: this solution’s five third-party credential parameters are all declared NoEcho, so CloudFormation already masks them in DescribeStacks output.

get_vp_record returns a fixed allowlist of diagnostic attributes. The meeting passcode, the VNC password, and the fields identifying who owns or shares the Virtual Participant are never returned — their names are reported so the agent knows the record was filtered and does not treat the absence as a finding, but their values do not reach the model or the thinking-step stream. A field added to the row in a future release is withheld until it is added to that list deliberately.

The record also comes with an endAssessment: a reading of the row the way the code that writes it does. A Virtual Participant ends in one of four ways, and each leaves a different shape. Ended through the end operation (by a user, the SDK or CLI), it has endedAt and endReason on its row, and its log has Received SIGTERM (and, on a MicroVM, [terminate] signalling app to exit) rather than a VP exit: line; the assessment presents that recorded reason as the answer to why it ended. Marked by the VP task reaper after its ECS task stopped (FARGATE and EC2 launch types), it is FAILED with endedAt but no endReason, and errorMessage carries the ECS stop code and reason; the assessment points at that instead. Leaving through its own exit path, it is COMPLETED or FAILED with an endTrigger, and its log has a VP exit: line. Stopped by a signal that did not come through the end operation, it is COMPLETED with none of these. A row whose status is not terminal but which has endedAt set describes a participant that has ended — a progress update it wrote while shutting down landed after the end — and the assessment says the status is stale. A scheduled participant cancelled before it launched never ran, and the assessment says there is no participant log to search. Every other assessment ends with the one log search that corroborates it: the participant’s id together with the markers for every way it could have ended, in one call, with a lookback_hours reaching back to the row’s createdAt, because the default search window is only a few hours.

A search that returns nothing says which window it covered, that its terms are ORed so alternatives belong in the same call, and — when it was looking for VP exit: — which lines a participant stopped from outside writes instead. These hints are in the tool results rather than only in the prompt, so a deployment that has replaced the prompt still gets them.

Two design points worth knowing, because they are what make the answers trustworthy:

Log group names are discovered, never constructed. An LMA deployment’s log groups sit in four different namespaces: most are named after the generated nested-stack name, a few after the parent stack, the MicroVM groups live under /aws/lambda-microvms/, and AppSync’s group is named after the API id. The agent refuses to query a name that discover_log_groups did not return, because a guessed name produces an empty result that reads exactly like an absence of evidence. On a stack upgraded from a release before v0.4.0 it also finds the MicroVM log groups that release used, /aws/lambda-microvms/<stack>-vp and -asr, which the upgrade leaves in place. Where a MicroVM’s output goes is fixed when the MicroVM is launched, so a Virtual Participant launched before the upgrade finished — whichever image it ran on — logged only there. Each MicroVM group is labelled current or legacy, and when a legacy group exists the agent is told to search it before concluding there is no evidence (see the v0.4.0 migration notes).

VPLaunchType is a first-class input. Under the default MICROVM, the Virtual Participant’s Fargate log group exists and is permanently empty and no ECS task-stopped event is ever emitted. An agent that did not know this would report “no evidence the Virtual Participant ran” on a perfectly healthy deployment. It reads the parameter first and routes accordingly.

It also reports, for every log group, whether CloudWatch currently stores any bytes for it. That is a hint about where to look first rather than proof that a path is unused: a group reports no stored bytes when everything in it has aged past the retention period too, so a participant idle for a fortnight and failing today would report none on the very group holding the failure. The agent is told as much, and told that “does this deployment use that path” is a question for the stack parameters rather than for a byte count.

Discovery is scoped to this deployment, and says so when it cannot be. The agent resolves your stack’s own nested stacks by name before looking for log groups, so an account holding both LMA and LMA-dev never gets the second one’s log lines reported as the first one’s evidence. If that lookup is not possible it falls back to matching on the stack-name prefix and tells the agent that a neighbouring deployment’s groups may be included, rather than degrading silently. Likewise, if the TROUBLESHOOTING_MAX_LOG_GROUPS cap cuts the list short, the agent is told the list is incomplete so a group it cannot see is not read as a group that does not exist.

Tuning the prompt

Section titled “Tuning the prompt”

The agent’s judgement is its system prompt, and the prompt is meant to be edited. It lives in DynamoDB, in the same table as the summarization prompt templates, as a Default/Custom pair:

ItemBehaviour
DefaultTroubleshootingAgentPromptShipped with the stack and rewritten whenever a stack update ships a changed prompt. Edits to it are lost.
CustomTroubleshootingAgentPromptCreated empty if it is absent, on create and on update, so it is there on an upgraded deployment as well as a new one. Once it exists it is never written again, so your prompt survives every later upgrade.

To override it, set a systemPrompt attribute on CustomTroubleshootingAgentPrompt. The change applies to the next diagnosis — no redeployment, no Lambda update. Removing the attribute, or setting it to an empty string or NONE, reverts to the shipped default. The stack output TroubleshootingAgentCustomPrompt is a direct link to that item in the DynamoDB console; <br> is accepted as a line break there, since the console has no good way to type one.

A very short value is treated as a truncated paste rather than a prompt and the default is used instead. If neither item holds a usable prompt the agent refuses to run rather than improvising one — an agent that has not been told what LMA does not persist reads an empty log group as evidence.

The shipped prompt’s error-pattern catalogue is seeded from this project’s own CHANGELOG history, in rough order of how often each class has actually occurred: meeting-platform UI drift, end-of-meeting misdetection, audio-pipeline silence or duplication, speech-session lifecycle on long meetings, voice assistant session management, fresh-deploy permission and key gaps, URL-unsafe characters in meeting identifiers, and capacity or quota limits.

Cost, and the limits that bound it

Section titled “Cost, and the limits that bound it”

Every run is bounded in four independent ways, and all four are enforced in code rather than requested in the prompt. There is deliberately no whole-run retry: a failed run is reported once, because restarting a diagnosis from the original question re-pays for every tool call it already made.

When a limit is reached, the agent is first asked to write its answer from the evidence it has — the cooperative path, and the one that produces a real diagnosis. Every tool call the model made in that same turn gets the same request, because a model can ask for several tools at once and none of them can have ignored an instruction it had not yet seen. If the model calls a tool in a later turn anyway, the run is ended rather than paying for a further model turn, and you get a diagnosis in the usual three sections whose Root Cause is “Not determined” and which names the limit that was reached.

The run is ended through the Strands Agents SDK’s own stop request, which takes effect after every tool call in the turn has been given a result, so the conversation the model would see stays complete. This behaviour is tested against the real Strands event loop with a scripted model in place of Bedrock (lma-meetingassist-setup-stack/test/test_troubleshooting_real_strands.py).

The response’s JSON-encoded body reports both outcomes. truncated is true whenever a limit was reached at all, on the cooperative path as well as the forced one, so read it as “this diagnosis did not get to search as widely as it wanted” rather than “the agent was cut off mid-sentence”. usage.endedBecause is set only on the forced path, and names the limit that ended the run.

The per-turn output limit works differently, because it is reached inside a model turn rather than between tool calls. Claude 5 generation models reason before they answer, and that reasoning counts against the limit, so the answer turn after a long investigation is the one most likely to reach it. When a turn does, the run is not resumed (that would re-send the whole conversation): if the model had begun its answer, you get the answer as far as it got, ending with a note that it stopped at the output limit; if it had not, you get the three-section “Not determined” answer naming that limit. The model’s reasoning is never part of either. Both set truncated and usage.endedBecause.

Environment variableDefaultMaximumBounds
TROUBLESHOOTING_MAX_ITERATIONS820Tool calls per diagnosis
TROUBLESHOOTING_TOKEN_BUDGET250,0001,000,000Input + output tokens per diagnosis. Checked between tool calls, so a run can overshoot it by roughly one model turn before it stops
TROUBLESHOOTING_WALL_CLOCK_SECONDS240870Seconds per diagnosis — requested; see below
TROUBLESHOOTING_ANSWER_RESERVE_SECONDS30120Time held back for the model to write its answer
TROUBLESHOOTING_MAX_OUTPUT_TOKENS16,38432,768Output tokens per model turn, reasoning included. Applies to Claude models; the Amazon Nova models are held to at most 4,096
TROUBLESHOOTING_MAX_LOG_GROUPS120400Log groups returned by discovery
TROUBLESHOOTING_MAX_LOG_EVENTS1001,000Rows per log query
TROUBLESHOOTING_MAX_LOG_MESSAGE_LENGTH2,00020,000Characters per log line
TROUBLESHOOTING_MAX_TOOL_RESULT_CHARS24,000120,000Characters per tool result
TROUBLESHOOTING_DEFAULT_LOOKBACK_HOURS472Search window when none is asked for
TROUBLESHOOTING_MAX_LOOKBACK_HOURS72336Largest search window allowed
TROUBLESHOOTING_QUERY_TIMEOUT_SECONDS45120Seconds to wait for one log query
TROUBLESHOOTING_QUERY_POLL_SECONDS110Seconds between polls of a running query

Set these on the STRANDS-<stack>-Troubleshooting Lambda function. They take effect on the next invocation. A value above its maximum is clamped rather than refused, and an unreadable value falls back to the default, so a typo costs money or precision rather than stopping a diagnosis from starting — and every clamp or fallback is logged, so a limit never quietly becomes a different one.

⚠️ These are not carried in the CloudFormation template, so a value you set by hand does not survive a stack update — CloudFormation restores the function’s environment to what the template declares, which is none of these. That is deliberate: they are a dozen cost knobs for an operator looking at a specific run, not deployment configuration, and adding a dozen stack parameters for them would be worse. Treat a change here as temporary. The one setting that is meant to persist is the system prompt, which lives in DynamoDB precisely so that it does.

The wall clock is a request, not a guarantee of how long a run may take. The effective budget is the smaller of TROUBLESHOOTING_WALL_CLOCK_SECONDS and the time the invocation actually has left, less TROUBLESHOOTING_ANSWER_RESERVE_SECONDS for the final model turn. So raising the wall clock above the function’s Timeout does not extend a run — it is simply ignored, and the agent still reports that it ran out of time rather than being killed mid-answer. To genuinely allow longer diagnoses, raise the function’s Timeout as well. Each run logs the effective budget it used and whether the invocation was what capped it.

TROUBLESHOOTING_MAX_LOOKBACK_HOURS is the costliest of these: CloudWatch Logs Insights bills by bytes scanned, and the Virtual Participant’s container log group is the highest-volume stream in the solution.

The agent uses the same Bedrock model as the Meeting Assistant — the Meeting assistant model in the Amazon Bedrock Models section of the Configuration page — so selecting a stronger model there gives a stronger diagnosis. Each run reads the model as it starts. Its token usage is logged at the end of every run.

Guardrails and what it will not say

Section titled “Guardrails and what it will not say”

If BedrockGuardrailId and BedrockGuardrailVersion are both set, the configured Amazon Bedrock Guardrail is applied to this agent as it is to the Meeting Assistant. With either one unset, no guardrail is applied.

The prompt also instructs the agent, in its output: to describe a defect as the behaviour observed in neutral engineering terms rather than characterising it in security terms; to redact credentials, tokens and signed URLs from the evidence it quotes; and to quote meeting content only where the content itself is the evidence. This matters because a diagnosis is the kind of text people paste into a public issue tracker. If what the agent finds needs reporting through a security channel, it is told to say so and stop rather than write it up.

Those are instructions to a model, so the controls that do not depend on it sit in the tools: get_vp_record’s field allowlist, the parameter redaction described above, and the thinking-step stream’s summaries.

That stream matters most, because it reaches the UI without the model in the loop, so nothing the prompt says about what to quote applies to it. The rule it follows is: publish a shape, a count, or text written by this codebase — never text the model wrote, and never an AWS error message.

In practice a progress line reads “2 log groups, 42 rows, 90000 bytes scanned” or “3 log groups in virtual-participant, transcript-pipeline”. A query_string, search_terms or components the agent wrote appears only as a length, because it writes those from text it has just read out of a log line. Log group names are counted and reported by which component they belong to rather than quoted, because a name on this stream has not been checked against discovery yet. A failed call publishes the exception type, or a short label written at the point the error is raised — not the message, which may carry an account-specific ARN. The agent itself still receives all of it; this is about what leaves the function.

The same applies to an error response: a 400 or a 500 carries a fixed message and an errorType, and the full text goes to the function’s log. That matters because the troubleshooting resolver forwards that message to the browser.
