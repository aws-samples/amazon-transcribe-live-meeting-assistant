Meeting Cost Estimate

Meeting Cost Estimate

Section titled “Meeting Cost Estimate”

LMA estimates what each meeting cost to run, line by line: the seconds of Amazon Transcribe it used, the tokens every Amazon Bedrock call spent on it, and the compute of the Virtual Participant that joined it. The approach follows the GenAI IDP Accelerator’s estimated cost per document: usage is recorded where it happens as metering records against the meeting, and a configurable price table turns those records into dollars whenever the estimate is read.

It is an estimate, and it is labelled as one wherever it appears. It uses public on-demand list prices dated in the price table, the first volume tier of any tiered price, and only the usage LMA meters. What is not included lists what is left out, and the estimate itself carries the same list.

Where to read it

Section titled “Where to read it”

On the meeting page

Section titled “On the meeting page”

The meeting page’s header shows the total as Est. cost (“$0.1234”, with “(incomplete)” when some line has no price); selecting it opens the itemised estimate. The same estimate is the Estimated cost section of the Details tab — collapsed by default, below the Speakers and Consent panels — which shows the total in its header (“$0.1234 estimated”) and, opened, the itemised table:

ColumnShows
ServiceThe service and model or API, grouped by what the usage was for, with a subtotal row per group. Select a service to see how its usage was measured (launch type, sizes, why a figure is approximate).
Unit, QuantityWhat was counted and how much.
Unit priceUS dollars per unit from the price table, or No price when the table has none.
Estimated costQuantity times unit price. Below $0.0001 is written ”< $0.0001”, never rounded to zero. Units that are shown for reference only read “not billed separately”.

Above the table the panel says that this is an estimate, the date of its prices, and any line it could not price or region it priced at another region’s rates. Below it are what the estimate does not include, the region, and when the figure was computed. The estimate is re-read when the meeting’s status changes and when its summary arrives, because most of a meeting’s usage is recorded as it ends. A Virtual Participant writes its runtime as it leaves, which can be later still; the refresh button picks that up. A meeting with no metering records shows No metering data rather than a cost of zero.

Through the API

Section titled “Through the API”

Query.getCallCost(CallId) on the AppSync API returns the itemised estimate for one meeting. It answers the same callers getCall answers: an Admin, the meeting’s owner, anyone the meeting is shared with, and a backend role signing with IAM.

The result has:

FieldMeaning
TotalCostThe sum of every priced line, in Currency (USD).
ContextTotalsThe same total split by what the usage was for (see the contexts below).
ItemsOne line per context, service and unit: quantity, unit price and cost.
UnpricedCountLines with no price in the table. They are left out of every total, so a non-zero count means the total is incomplete.
RecordCountHow many metering records were read. Zero for a meeting held before this feature was deployed.
PricesAsOf, PriceSourceWhen the default prices were taken, and from where.
Region, BaseRegion, RegionsWithoutListedPricesThe deployment’s region, and any region whose usage was priced at the base region’s prices because the table lists none of its own.
NotIncludedWhat the estimate leaves out.
ComputedAtWhen this estimate was computed.

The estimate is computed on every read, not frozen when the meeting ends. Usage keeps arriving after the END event: the summary is generated after it, the Virtual Participant writes its runtime as it leaves, and a summary can be regenerated days later. A meeting’s records are one DynamoDB query on one partition, so reading them each time is cheap, and the figure is always the current one.

What is metered, and how

Prices

Section titled “Prices”

The default price table is lma-ai-stack/source/lambda_functions/configuration_seeder/defaults/CallPricing.json. Every price in it is a public on-demand list price read from the AWS Price List API (AmazonBedrock, AmazonBedrockFoundationModels, transcribe, AWSLambda, AmazonECS, comprehend) on 2026-10-28, in US dollars per single unit — per token, per second, per vCPU-second. Where a price is tiered by monthly volume, the first tier is listed, which is the highest price; a deployment that transcribes more than 250,000 minutes a month pays less than this shows for the Transcribe add-ons. Standard streaming transcription is a flat price.

A few examples of what is in it, for us-east-1:

The table holds a price for every Bedrock model the stack parameters offer, under its exact model or inference-profile id. A global. and a us. profile of the same model have different prices (where both exist, the regional us. profile is 10% higher), so each is listed separately. A test fails if an Amazon Nova or Anthropic model id is added to lma-main.yaml without a price.

Bedrock reports prompt-cache tokens separately from ordinary input, and they are billed at their own rates, so a Bedrock line can carry cacheReadInputTokens and cacheWriteInputTokens beside inputTokens. The table prices both for every model the meeting assistant caches on, which includes every Claude model the summarizer caches on. Nova Micro, Nova Lite and Nova Pro list a cache write at zero and a cache read at a quarter of the input price; those three cache prices were read from the Price List API on 2026-11-06, after the rest of the table.

Regions

Section titled “Regions”

Prices are listed for us-east-1 and us-west-2. regions.default holds the us-east-1 prices, and regions.us-west-2 lists only what differs there (Nova Sonic’s text tokens). A deployment in any other region is priced at the us-east-1 prices, and its estimate names the region in RegionsWithoutListedPrices. To price another region, add a regions.<region> entry holding its differences from the base; a region whose prices equal the base is recognised by listing it in pricedRegions. Either one is enough for the region to count as priced.

How a line is priced

Section titled “How a line is priced”

The lookup is deliberately strict, as it is in the IDP Accelerator: a line’s service must match a price entry exactly, and its unit must be named in that entry. Nothing is guessed from a similar-looking entry. A line with no price is reported as unpriced, shown without a cost, left out of every total and counted in UnpricedCount. A plausible wrong number is worse than a visible gap.

One exception, for Amazon Bedrock models, is always named on the line it applies to. The price table lists each model’s global. and us. profiles and its plain id where Amazon Bedrock sells one, while the Model inference geography setting (see Where meeting content is processed) can also run the same model through its eu., apac., jp., au., ca. or in. profile, or as its plain in-Region id. A line for such an id is priced at the same model’s global. price, else its plain id’s, else its us. profile’s, and its note says which. It is never priced as a different model. For the models in the shipped table the us. profiles are listed at 10% above the global. ones, so an estimate for a geography profile priced this way is likely low by about that much.

A unit named in nonChargeableUnits (the images the meeting assistant sends, for example) is shown with no cost and is not counted as unpriced. Changes to the price table replace a list rather than merging into it, so a custom nonChargeableUnits must list every such unit, images included.

Changing a price

Section titled “Changing a price”

An Admin can change prices in the Meeting Cost Prices section of Configuration ▸ Configuration (/#/configuration/settings?section=call_pricing), where each price that differs from the shipped one is marked and can be reset; see the Configuration Guide. The same changes can be made through the API, as described below.

The price table is the call_pricing section of the unified configuration store. The shipped table is part of the baseline record, so a release that updates a price reaches every deployment on its next stack update. An Admin’s changes are stored as a delta in the custom profile and keep winning over the baseline:

  • Query.getCallPricing returns the shipped table (Default), the Admin’s changes (Custom), the merged table every estimate uses (Effective) and the Version to send back on save.
  • Mutation.updateCallPricing(input: {Pricing, ExpectedVersion}) stores the changes. Pricing is a JSON object in the same shape as the shipped table, naming only what differs — for example {"regions": {"default": {"transcribe/streaming": {"seconds": 0.00012}}}} for a negotiated Transcribe rate. "{}" returns every price to the shipped value. The save replaces all of the Admin’s earlier price changes with this object, so include every change that should stay. The save is checked against the call_pricing section’s schema and refused as a whole, naming each problem, if a price is not a finite, non-negative number, a region, service or unit name is not in the form the table uses (a region is default or a code such as us-east-1, a service is <service>/<api-or-model>, a unit is a word such as inputTokens), currency is anything but USD, pricesAsOf is not a YYYY-MM-DD date, or a key is one the table does not have. ExpectedVersion is required, and a save against a version another Admin has since saved is refused rather than overwriting their change. The version is that of the whole custom profile, which the Transcript Summary page also writes, so a price save made after an unrelated prompt-template save is refused too; reload and save again.

Both are Admin only. An estimate read within five minutes of a price change may still use the previous price: the section is on the store’s standard cache tier.

What is not included

Section titled “What is not included”

The estimate covers the usage that can be attributed to one meeting. It does not include:

  • Resources that run whether or not a meeting is in progress: the WebSocket transcriber’s Fargate service, NAT gateways, the Application Load Balancer, CloudFront, and Virtual Participant EC2 hosts.
  • Per-request charges of the services LMA is built on: AppSync, DynamoDB, Kinesis Data Streams, LMA’s own Lambda functions, S3 storage of recordings, and CloudWatch Logs.
  • Amazon Bedrock Knowledge Base queries made by the meeting assistant’s document and meeting-history tools (RetrieveAndGenerate does not report token usage), and the vector store behind them.
  • Amazon Bedrock Guardrails and Amazon Translate (live translation in the browser).
  • The short Nova Sonic clip the voice assistant renders once at start-up to acknowledge tool calls.
  • Lambda MicroVM snapshot read and storage charges.
  • Third-party services: ElevenLabs, Simli and Tavily web search.
  • Free tier, Savings Plans, volume tiers beyond the first, and any private pricing agreement.

Known ways the figure can be off

Section titled “Known ways the figure can be off”
  • Lost records read as lower cost. A metering write that fails is logged and dropped rather than allowed to interrupt transcription or a summary, and a process that is killed outright (out of memory, a host reboot) writes nothing for its open request or its runtime.
  • Redelivery can count Comprehend twice. The sentiment counter adds on each delivery of a transcript segment, so a Kinesis batch that is redelivered adds its segments’ units again. The amount is a fraction of a cent.
  • A re-run upload finalizer records its batch job again. The finalizer writes the job’s seconds each time it finalizes the meeting, so finalizing the same upload twice shows the batch transcription twice.
  • Compute is measured from inside the process. Fargate’s image pull and start-up, and the seconds between a MicroVM launch request and the Virtual Participant process starting, are billed but not counted.

How the records are stored

Section titled “How the records are stored”

Metering records are items in the meeting table (EventSourcingTable) under PK = mtr#<CallId>, one item per metered event:

AttributeMeaning
SK<Context>#<RecordedAt>#<RecordId>, unique per record. The Comprehend counter uses the fixed Sentiment#counter#comprehend/detect-sentiment.
CallId, Context, ServiceThe meeting, what the usage was for, and the price-table key.
UsageMap of unit to quantity. The counter item keeps each unit as a top-level u_<unit> number instead, because DynamoDB’s ADD cannot create a member of a map that does not exist yet.
DetailsStrings for the reader: launch type, sizes, how a duration was measured. Never priced.
RegionThe region the usage was billed in, when not the deployment’s.
Source, RecordedAtThe component that wrote it, and when.
ExpiresAfterThe same retention as the meeting record (MeetingRecordExpirationInDays, or the shorter period set in the Retention section of the Configuration page), so a meeting’s cost expires with it.

The grant each component gains for metering is dynamodb:PutItem on the meeting table, conditioned on dynamodb:LeadingKeys matching mtr#*, in addition to whatever access that component already had, so the only write it adds is of metering records. (The call event processor, which already has full access to the table, uses UpdateItem for its counter.) Deleting a meeting from the UI deletes its metering records with it; a record a Virtual Participant writes while it is being stopped by that same deletion can land after the delete, and expires with its TTL.

The writers are lma_metering in the AI stack’s configuration layer (the Lambda functions), a copy of its writer in the meeting-assist stack, and metering.ts in the WebSocket transcriber and the Virtual Participant. lma-ai-stack/test/test_metering_record_contract.py asserts they all produce the same item, and that every service the TypeScript writers name has a price.

Upgrading

Section titled “Upgrading”

Nothing to do. Meetings held before the upgrade have no metering records, so their estimate reads zero with RecordCount: 0 — which means “not metered”, not “free” — and the meeting page shows No metering data for them.
