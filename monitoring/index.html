Monitoring & Alerting

Section titled “Monitoring & Alerting”

LMA deploys an SNS topic for operational alerts, 15 alarms that notify it, and one CloudWatch dashboard per deployment. Everything described here is created by lma-main.yaml as part of the normal stack deployment — there is nothing extra to install — but one manual step is required before any alert is delivered: the email subscription SNS creates for your AdminEmail address starts in PendingConfirmation and stays there until somebody clicks the link in the confirmation message. See Subscribing to the alerts topic.

For log groups, console navigation and the symptom-by-symptom guide to specific failures, see Troubleshooting. This page covers what is watched automatically and who hears about it.

What is watched

Section titled “What is watched”

The alarms fall into two groups, and the difference matters when you are reading one.

All but two read a metric that an AWS service publishes on its own. None of those depend on LMA emitting anything, which means they work on a deployment that has never been touched and they keep working if application code changes. They cover infrastructure health well and application behaviour only indirectly: they can tell you the Call Event Processor is failing, but not that a particular meeting produced no transcript.

The remaining two read metrics LMA publishes itself — see Metrics LMA publishes below. Both watch a condition the code otherwise swallows: a failure that is caught, recorded and not raised, so no AWS-published metric moves and nothing else would ever mention it. That is exactly why each is an alarm rather than only a graph. The cost of reading an application metric is that it depends on application code: if a component stops publishing, its alarm reads OK. Both treat missing data as not breaching, so an alarm with no data at all looks exactly like one that is simply quiet and will not be the thing that tells you. A build-time gate checks the wiring that would cause that, and the dashboard band note says how to tell the two apart by eye.

Each alarm carries an AlarmDescription written as the first few steps of a runbook, because the description is the only context that travels with the notification email. If you receive an alert and want to know what to check, read the body of the message before opening the console.

Notes on individual alarms

Section titled “Notes on individual alarms”

Queue depth is not a rate. Nothing drains the discarded-records queue automatically; messages sit there for their 14-day retention. So discarded-records-queue-depth does not clear on its own — the depth stays where it is until somebody purges the queue. That is why it also notifies on recovery: the queue returning to empty means a person acted, which is itself worth knowing. The message bodies carry the shard and sequence-number range of the failed batch rather than the records themselves, so finding out what was lost means reading the Call Event Processor’s log group for the same period.

The concurrent-streams threshold cannot read your quota. Amazon Transcribe’s default account quota is 25 concurrent streaming sessions, and TranscribeConcurrentStreamAlarmThreshold defaults to 20 — eighty per cent of it, which leaves time to request an increase before meetings start being refused. If you raise the quota, raise this parameter with it. There is no API the alarm can consult, so left at 20 against a quota of 200 it notifies at a level that is no longer close to anything. LMA opens one streaming session per audio channel, which means a stereo meeting counts as two.

What that alarm counts, exactly. Amazon Transcribe publishes ConcurrentStreamsCount under a single dimension set — Domain, ServiceType and Operation together — so the alarm is scoped to one operation, StartStreamTranscription, which is the one LMA calls. The count is still account-wide and region-wide: another workload in the same account calling StartStreamTranscription is included. A workload calling StartCallAnalyticsStreamTranscription or StartMedicalStreamTranscription consumes the same quota but publishes a separate series, so it is not included — if you share the account with such a workload, the alarm will under-report how close you are. Covering every operation at once would need a SEARCH expression, and CloudWatch does not accept SEARCH in an alarm, so enumerating one operation is the only option. The dashboard’s widget has the same scope.

A fresh install produces one stale-meeting-reaper-not-invoked alert. That alarm watches for the absence of invocations, so it treats missing data as breaching. CloudWatch treats an evaluation range with no data at all as breaching regardless of how many evaluation periods are configured, so a stack that has just been created notifies once and then clears as soon as the reaper’s first scheduled run lands. This is expected and needs no action. The reaper is always scheduled, so the alarm is created whenever operational alarms are on. Setting Meeting Processing › Minutes without speech before a meeting is ended to 0 on the Configuration page makes each run end nothing, but the reaper still runs on schedule, so the alarm does not stay red.

Healthy-target count and task count are a pair. An ALB target group publishes HealthyHostCount only while it has registered targets, so when the transcriber service has no tasks at all the target group publishes nothing and transcriber-no-healthy-targets reads as healthy. transcriber-service-no-tasks is what covers that case. Treat the two as one signal: either firing means new meetings are being refused.

vp-launch-failures watches the launch, not the meeting. It reads the Step Functions state machine that starts a Virtual Participant, so it tells you a bot was asked for and did not start. It cannot tell you that a bot started, joined, and then left early — ECS publishes no metric for a task that stopped unexpectedly, and the launch-and-admission detail lives in the Virtual Participant’s own log group and meeting record.

transcript-segment-write-failures is the only notice that a transcript has a gap. The Call Event Processor issues the writes for a batch of segments together and collects the results, including the failures, rather than raising on them. That is deliberate — one rejected segment should not replay the whole Kinesis batch — but the consequence is that the record is not redelivered, which is what sets these failures apart from every other failure in the pipeline. A raised failure is attributed to its record, retried, and finally described to the event source’s on-failure destination, where the discarded-records-queue-depth alarm picks it up. This one reaches neither on its own account, so that queue stays empty. It is redelivered only if some other record in the same batch raises, which redelivers everything after it.

AWS/Lambda Errors does not move for either, so it cannot be used to tell them apart: a raised failure that the batch processor can attribute to a record still leaves the invocation returning a partial-batch response normally. It moves only where a failure carries no sequence number at all, which is the one case the handler fails the whole invocation for. The transcript simply has a line missing, on a meeting page with no error on it.

If this alarm fires, read the Call Event Processor’s log group for max retries on query over the same window; each of those lines carries the exception type and the GraphQL errorType. Search for that string rather than the handler’s event processor error, which reports only failures that were raised — and the point of this metric is that these were not, so grepping for it finds nothing in the window that fired. Segments already lost cannot be replayed once their Kinesis records pass the stream’s 24-hour retention, so a sustained rate is urgent in a way a single occurrence is not.

meetings-without-transcript deliberately ignores short sessions. The transcriber counts a session only if it ran for at least thirty seconds and produced nothing, because below that the overwhelmingly common case is somebody who started streaming and changed their mind. The alarm then needs three in a five-minute window, so one genuinely odd meeting does not page anybody while a pattern does. The usual causes, in the order worth checking: the Amazon Transcribe concurrent-stream quota being exhausted, which transcribe-concurrent-streams-near-quota should have notified first; a language code or custom vocabulary the account does not have; and, where the MicroVM ASR engine is selected in the Transcription Engine section of the Configuration page, an engine that could not start with fallback to Amazon Transcribe switched off.

What it cannot see: meetings that do not go through the transcriber. A Virtual Participant runs Amazon Transcribe, or the MicroVM ASR engine, inside its own container and writes transcript segments straight to Kinesis, so a Virtual Participant that joins a meeting and transcribes nothing is not counted here and this alarm will not fire for it. The same goes for an uploaded recording. For a deployment whose meetings are mostly Virtual Participant ones, this alarm covers very little — the Virtual Participant publishes no transcript metrics of its own yet, which is the first gap named under What is not published yet.

One case to expect noise from: a transcriber task replaced mid-meeting, by a deployment or by scale-in. Its shutdown closes the server, which closes each connected socket, which runs the same per-meeting teardown a client disconnecting would — so a meeting it had carried for more than thirty seconds without a transcript yet is counted, even though what ended it was the infrastructure and not a transcription fault. Whether the count lands is a race: the process exits as soon as the server has closed, and the teardown runs from an asynchronous close handler. So treat a small number of these concurrent with a deployment or a scale-in event as explained by it, and read transcriber-service-no-tasks and the ECS task-count widget alongside. The alarm needs three in a five-minute window partly for this reason.

Why there is no alarm on how long a transcript takes to appear. TimeToFirstTranscriptSegmentMs is the obvious thing to alarm on and the wrong thing. It measures from a meeting’s audio session opening to its first transcript segment, and what dominates that interval is when somebody first speaks — so a meeting that starts five minutes before anybody talks produces a five-minute value, and a threshold low enough to catch a real problem would fire on every quiet meeting. The failure worth alarming on is “no transcript at all”, which meetings-without-transcript counts directly. The latency is graphed instead, where its distribution is informative and a single value is not.

Metrics LMA publishes

Section titled “Metrics LMA publishes”

Two of the alarms above, and one band of the dashboard, read metrics the application emits rather than metrics an AWS service emits. There are eight of them. Seven answer one question end to end: a meeting was asked for — did a transcript come out of it, how long did that take, and was anything dropped on the way? The eighth, from the Virtual Participant, counts the Nova Sonic voice assistant streams Amazon Bedrock refused for the account’s concurrency quota.

They are published in the CloudWatch namespace <stack-name> — the name of the top-level LMA stack, so two deployments in one account never mix. Each emitting component is told that namespace by a METRIC_NAMESPACE environment variable, which is what makes the dashboard and the alarms work on any stack name without being edited.

See Nova Sonic Concurrency Quota.

How they are published, and what that implies

Section titled “How they are published, and what that implies”

The records are written in CloudWatch’s embedded metric format: a line of JSON in the emitting component’s own log group, which CloudWatch Logs turns into a metric at ingestion. Nothing calls PutMetricData, and no IAM role gained cloudwatch:PutMetricData — AWS documents the embedded format as needing only the log-writing permission these components already have. Three consequences are worth knowing before you read a graph:

  • The log group is the audit trail. Every datapoint is still a log event, so a number you do not believe can be traced to the record that produced it with a Logs Insights query over the Call Event Processor’s or the transcriber’s log group, filtering on the metric’s name.
  • A count can be slightly out, in either direction. AWS documents the format as guaranteeing at-least-once delivery with occasional duplicates, so any of these can read high. Two have their own reasons to drift. MeetingsStarted can read low: it skips a start event that finds the meeting already stored, and a first delivery whose own earlier attempt stored the meeting and then failed in transit is indistinguishable from a redelivery. TranscriptSegmentsWritten can read high: when one record in a Kinesis batch raises, every record after it is redelivered, and segments already written by those later records are written and counted again. None of these is a billing input, so the trade is the right one — but do not read either as an exact census.
  • Datapoints can arrive a little late, because the log has to be flushed and ingested first, and neither Lambda nor the ECS awslogs driver lets the application control when. Both alarms on these metrics therefore need only one breaching period out of the last three, which is what AWS recommends for this case: it absorbs a datapoint landing in the period after the one it belongs to without missing the event.

What is not published yet

Section titled “What is not published yet”

The MicroVM ASR engine and the Meeting Assistant publish nothing, and the Virtual Participant publishes only NovaSonicStreamsThrottled. That means there is still no metric for the fraction of Virtual Participant joins that fail and on which trigger, for how often ASR falls back to Amazon Transcribe, or for assistant and Bedrock latency and failure rates. The Virtual Participant is the significant one: it transcribes in its own container rather than through the transcriber, so none of the three session metrics above covers a Virtual Participant meeting, and the equivalent of StreamingSessionsWithoutTranscript for it does not exist.

All of it remains diagnosable only from the log groups Troubleshooting names. It is a separate piece of work, deliberately: the Virtual Participant’s exit-reason taxonomy wants to be a metric dimension, and whether its value space is closed enough to be one needs checking before it becomes a billed dimension on a custom metric.

Subscribing to the alerts topic

Section titled “Subscribing to the alerts topic”

The stack creates one SNS topic, encrypted with the deployment’s customer-managed KMS key. Its ARN and a console link are stack outputs:

  • SNSAlertsTopicARN
  • SNSAlertsTopicConsoleUrl

An email subscription for the AdminEmail address is created with the stack. SNS email subscriptions start in PendingConfirmation and deliver nothing until confirmed. SNS sends a message titled “AWS Notification - Subscription Confirmation” to that address, with a link that must be clicked; until somebody does, every alarm can fire and nobody will hear about it. Check the subscription’s status on the topic’s Subscriptions tab in the console — if it reads PendingConfirmation, look for that email, including in a spam folder, and use Request confirmation on the subscription to send it again if it has been lost. The confirmation link expires after three days.

A headless or CI deployment therefore starts with no working subscriber, even though the subscription resource exists: nobody is reading the mailbox that was asked to confirm. If you deploy from a pipeline and want alerts, add a subscription after deployment that needs no human confirmation — an HTTPS endpoint, a Lambda function, or an SQS queue are all confirmed automatically — rather than relying on the email one.

Alerting a team rather than one person

Section titled “Alerting a team rather than one person”

The AdminEmail subscription is a starting point, not a design. One person’s mailbox is a single point of failure for every alert this stack raises, and it is also an address that eventually belongs to somebody who has left. Point the topic at something the team owns:

  • A distribution list or shared mailbox. Add a second email subscription for the alias and confirm it from the shared mailbox. Both subscriptions can coexist; remove the individual one once the alias is confirmed.
  • A chat channel. AWS Chatbot subscribes to an SNS topic and posts to Slack or Microsoft Teams, which also gives you a visible history of what fired and when. Configure it against the SNSAlertsTopicARN output.
  • An on-call system. PagerDuty, Opsgenie and similar accept an SNS subscription over HTTPS. Those subscriptions confirm themselves, so they work for a pipeline-deployed stack.
  • A queue, for anything that should be processed rather than read. An SQS subscription lets you fan out to your own tooling without giving that tooling permission to the topic.

Because the topic is encrypted with the customer-managed key, anything you give permission to publish to it also needs kms:GenerateDataKey* and kms:Decrypt on that key. Subscribers do not: decryption happens before delivery. The stack’s key policy already grants CloudWatch those two actions, which is what lets an alarm action reach an encrypted topic. The grant is not narrowed by a condition key, because AWS does not document CloudWatch populating aws:SourceAccount or aws:SourceArn when it calls KMS on an alarm action’s behalf, and a condition that did not match would drop every notification silently. If you deploy inside an AWS Organization and want that statement narrowed, aws:SourceOrgID is the condition key AWS documents for it.

Turning the alarms off

Section titled “Turning the alarms off”

EnableOperationalAlarms defaults to true. Setting it to false removes all of the alarms on a stack update and leaves the topic and the dashboard in place, which is the right choice if your organisation manages alarms centrally and would otherwise have two systems notifying for the same event. It removes the notifications rather than the visibility — the dashboard still works, because it reads the same service-published metrics directly.

One consequence worth expecting: because the topic and its subscription are created either way, a deployment with EnableOperationalAlarms=false still sends the AdminEmail address a subscription-confirmation message, for a topic that nothing will publish to. Confirming it anyway is the better choice — it means switching the alarms back on starts delivering immediately, rather than needing a second round trip through somebody’s inbox.

What it costs

Section titled “What it costs”

In us-east-1, a standard-resolution CloudWatch alarm costs $0.10 per alarm metric per month, with the first ten alarm metrics included at no charge. An alarm built on a metric-math expression bills per metric referenced in the expression, not per alarm, so the 15 alarms here are 17 billable alarm metrics — thirteen reading a single metric each, plus two metric-math alarms reading two metrics each. That is $0.70 per month for an account with the free allowance still available, and $1.70 per month for one that has already used it elsewhere.

The seven metrics LMA publishes are custom metrics, which are billed separately from the alarms that read them: $0.30 per metric per month in us-east-1 for the first 10,000, so $2.10 per month per stack, with the first ten custom metrics in an account included at no charge. None of them carries a dimension, which is the thing to keep an eye on if you add more: a custom metric is billed per unique combination of name and dimension values, so a dimension with a hundred values is a hundred metrics. Their records are also log events, so they add log ingestion and storage — a few hundred bytes per meeting and per batch of transcript segments, which is immaterial next to the transcript log volume itself.

The dashboard references 38 metrics, comfortably inside the metric allowance for a free dashboard, and CloudWatch includes three dashboards per account at no charge. An account that already has three custom dashboards pays $3.00 per month for this one, which is the realistic case for anyone running several LMA stacks in one account. Logs Insights queries in the four error-log widgets are billed per query when the widget runs, not continuously. See Amazon CloudWatch pricing for other regions and for current rates.

Read the shape, not a value: the interval is dominated by when somebody first speaks, so the minimum is the closest thing here to a measure of the pipeline itself, and a rising p90 with a flat minimum usually means meetings are starting earlier rather than the pipeline slowing.
Transcript segment writesTranscriptSegmentsWritten and TranscriptSegmentWriteFailed, annotated at the alarm thresholdWhether the transcript is reaching the meeting page. Any value on the failure series is a line that is simply missing, with no error on the meeting page and nothing on the discarded-records queue.
Audio sessions that produced no transcriptStreamingSessionsWithoutTranscript against StreamingSessionsStarted, annotated at the alarm thresholdSessions that streamed audio and got nothing back. Sessions under thirty seconds are not counted, so a value here is a session that ran long enough for silence to be a fault rather than a user who changed their mind — though a muted room or a meeting abandoned at minute two still lands here, which is why the alarm needs three in a window. Read against sessions opened: one in fifty is a different problem from one in two.
Nova Sonic streams refusedNovaSonicStreamsThrottledWhether this stack’s voice assistants are being refused Nova Sonic streams for the account’s concurrency quota of 20 per region. Each refusal degrades an assistant rather than failing it — see Nova Sonic Concurrency Quota for what each one does — so a value here is a capacity signal: fewer concurrent voice-assistant meetings in the account and region, or another region, is the remedy, since the quota cannot be raised.
Four error-log tablesThe most recent 50 lines matching /ERROR/ in the Call Event Processor, the Virtual Participant launch state machine, the Virtual Participant container and the WebSocket transcriber container log groupsA first look without leaving the dashboard. These are CloudWatch Logs Insights queries, so they run on demand and are billed per query, not continuously.
